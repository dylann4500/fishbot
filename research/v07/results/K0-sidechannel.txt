K0 -- the mechanical side-channel certification gate  (fish7 v7side)
FishBot v0.7 phase 3.  Main repository, HEAD 0c021a3 plus this patch.
Author: Dylan Nguyen, FishLab Research Project.

Command form:  ./fish7 v7side --a=<spec> --b=<opp> --games=N --seed=<bank> --threads=2
Banks: 7030001 (evaluation), 7030002 (replication).  709xxxx never touched (binary refuses, exit 5).
Exit code 0 = CERTIFIED, 1 = NOT CERTIFIED, 5 = sealed bank, 6 = mixSeed inverse round-trip failed.
Node sampling for S3/S5 is keyed off the DEAL INDEX, so every number here is thread-invariant.

The gate certifies FOUR tests, over ALL FOUR decision types of THREAT-MODEL 6.2.
  S6  seat isolation      -- every decision rebuilt from (own hand, public stream, reset seed)
                             alone, on a freshly spawned thread, after the game.
  S4  stream independence -- T10: a per-seat stream drawn independently of the deal.
  S5  posterior invariance-- exact posterior resample (DealDP + Belief::satisfies), scored as
                             P(hit|truth) vs P(hit|posterior).
  S3  listening substitution -- rule-equivalent public-action swap inside the bit-for-bit tie
                             group, with an OPPOSING-seat control running the same policy.
Thresholds (a priori, see research/v07/notes/K0-gate.md):  S3 asymmetry 15 pts AND 3 sigma;
S4 transcript identity for a deterministic policy, else win-rate CI containing 0 and ask hit
rate within 3 pts;  S5 gap 20 pts;  S6 zero mismatches.

PANEL E -- FOLLOW-UP ON THE ONE S6 MISMATCH.  The F-cheap search configuration is the
only member of the panel that has ever produced a nonzero S6 count.  Panel B (bank
7030001, 400 deals, all four tests) gave 0/262920; panel D (bank 7030002, same cell)
gave 1/264051 -- one ask decision, in one game of 800.

The mismatch is REPRODUCIBLE IN KIND and it depends on what else the harness does on
the worker thread.  Same command, 150 deals, bank 7030002:
    --tests=s6         -> 0/98816   (98816 decisions, thread-count-invariant at 1/2/4)
    --tests=s5,s6      -> 0/98816   (s5 builds DealDP only)
    --tests=s4,s6      -> 1/98792   (s4 plays a second game per deal on the thread)
    --tests=s3,s6      -> 1/98792   (s3 constructs and replays agents on the thread)
s3 and s4 give the IDENTICAL altered decision count, so the perturbation is not what
the extra work is, only that it happened.  s5 -- which touches DealDP's thread_local
scratch but never builds a BlockDP -- does not perturb.  That pattern is consistent
with THREAT-MODEL E-2, the BlockDP shared per-thread pool, and it is NOT root-caused
here; blockdp.hpp's stamp/generation guard and its sReady reset were both inspected
and are in place, so the mechanism is something else in that layer.
